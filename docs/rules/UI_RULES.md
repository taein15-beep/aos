# AOS UI / UX Rules

## 1. 기본 방향

AOS는 여행사 관리자용 ERP 시스템이다.

디자인의 핵심은 화려함이 아니라 업무 효율과 정보 가독성이다.

UI는 다음 원칙을 따른다.

- Clean
- Professional
- Compact
- Consistent
- Data Focused

---

## 2. 기본 화면 구조

관리자 화면은 기본적으로 다음 구조를 사용한다.

Header
+
Sidebar
+
Page Header
+
Search / Filter
+
Content
+
Pagination 또는 Action 영역

기존 공통 Header와 Sidebar를 페이지별로 새로 구현하지 않는다.

---

## 3. Page Header

페이지 상단에는 다음 정보를 배치한다.

페이지 제목

필요 시:
- 설명
- Breadcrumb
- 주요 Action 버튼

예:

예약접수현황

우측:
[예약등록]

---

## 4. 검색영역

ERP 검색조건은 카드 또는 구분된 영역으로 구성한다.

검색조건이 많으면 무조건 한 줄에 넣지 않는다.

권장:

1행
분류 / 기간 / 상태

2행
상품명·상품코드·예약자 / 판매점 / 담당자

우측 또는 하단:
[초기화] [검색]

검색 버튼을 가장 명확하게 표현한다.

---

## 5. Form

Label과 Input 관계를 명확하게 한다.

필수 입력값은 `*` 등으로 표시한다.

입력 항목의 의미에 맞는 컨트롤을 사용한다.

날짜:
Date Picker

상태:
Select

긴 설명:
Textarea

Boolean:
Checkbox 또는 Switch

---

## 6. Table

ERP의 핵심 UI는 Table이다.

다음 원칙을 따른다.

- Header 명확하게 표시
- 숫자 정렬 일관성 유지
- 금액 우측 정렬
- 상태 Badge 사용
- 지나치게 긴 텍스트 말줄임
- 필요한 경우 Tooltip 제공
- Action 영역 위치 일관성 유지

Table Header와 Body의 column 정렬이 어긋나지 않도록 한다.

---

## 7. 금액

금액은 천 단위 콤마를 표시한다.

예:

`230,000원`

가능하면 금액은 우측 정렬한다.

총액 등 중요한 값은 시각적으로 강조한다.

---

## 8. 인원

여행 인원은 기본적으로 다음 용어를 사용한다.

- 대인
- 소인
- 유아

예:

`대인 3 / 소인 1 / 유아 0`

필요한 경우 1인 요금을 함께 표시한다.

---

## 9. 상태 Badge

상태값은 Badge 형태로 표시할 수 있다.

단, 색상만으로 상태를 표현하지 않는다.

Badge 안에 반드시 상태 텍스트를 표시한다.

---

## 10. Button

버튼에는 명확한 행동을 표시한다.

좋은 예:

- 예약등록
- 저장
- 검색
- 인원변경
- 결제등록
- 환불처리
- 정산서
- 삭제

피해야 할 예:

- 확인
- 처리
- 실행

맥락상 의미가 불명확한 버튼명은 피한다.

---

## 11. 버튼 우선순위

Primary:
주요 저장/등록/검색

Secondary:
보조 기능

Danger:
삭제/취소 등 위험한 작업

한 화면에 Primary 버튼을 지나치게 많이 사용하지 않는다.

---

## 12. Modal

다음 작업은 Modal 사용을 우선 고려한다.

- 간단한 등록
- 인원변경
- 상태변경
- 메모
- 결제등록
- 간단한 확인

복잡한 업무는 Modal에 억지로 넣지 않고 별도 페이지 또는 Drawer를 검토한다.

Modal 기본 구조:

Title
→
Content
→
Cancel / Primary Action

---

## 13. 삭제 및 위험 작업

삭제, 예약취소, 환불 등 되돌리기 어려운 작업은 확인 절차를 제공한다.

예:

"예약을 취소하시겠습니까?"

가능하면 해당 대상도 표시한다.

---

## 14. 고객정보

전화번호:

`010-1234-5678`

날짜:

`YYYY-MM-DD`

날짜+시간:

`YYYY-MM-DD HH:mm`

예약번호 및 상품코드는 동일한 규칙으로 표시한다.

---

## 15. Loading

API 호출 등 시간이 필요한 작업은 Loading 상태를 제공한다.

사용자가 버튼을 여러 번 클릭하지 않도록 처리한다.

---

## 16. Empty State

데이터가 없는 경우 빈 Table만 표시하지 않는다.

예:

`등록된 예약이 없습니다.`

필요한 경우:

`[예약등록]`

버튼을 제공한다.

---

## 17. Error

오류 발생 시 사용자가 무엇을 해야 하는지 알 수 있게 안내한다.

나쁜 예:

`Error`

좋은 예:

`예약정보를 불러오지 못했습니다. 잠시 후 다시 시도해 주세요.`

---

## 18. 관리자 UI 일관성

예약관리에서 사용하는 Button, Table, Badge, Modal 등의 디자인은 상품관리와 정산관리에서도 가능한 동일하게 사용한다.

페이지별 독자적인 디자인 시스템을 만들지 않는다.

---

## 19. 화면 설계 우선순위

새 화면 설계 시 다음 순서로 판단한다.

1. 사용자가 가장 많이 확인하는 정보
2. 사용자가 가장 많이 수행하는 행동
3. 상태 확인
4. 검색
5. 상세정보
6. 부가 기능

---

## 20. 최종 원칙

AOS 화면은 사용자가 설명서를 읽지 않아도 업무 흐름을 이해할 수 있어야 한다.
